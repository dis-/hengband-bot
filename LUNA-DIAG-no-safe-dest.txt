WHY THIS IS A STOP
The behaviour is the documented and pinned design: the docstring of
_start_no_safe_destination_fundraising (policy.py:15902-15905) says the set is
"never opened at or above FUNDRAISING_GOLD_TARGET, where the gold set-end would
close it on the next board ... there the named depth-gate stop stays", and the
existing test pins it:

  tests/test_no_safe_destination_recorded.py
  NoSafeDestinationRecordedTest.test_unsafe_alternate_target_stops_like_angband_when_no_fallback
    gold = FUNDRAISING_GOLD_TARGET (15000)
    old (current) value:
      ("1", "town:blocked:depth-gate:destination-22:missing-resist_conf")
      ("1", "town:blocked:depth-gate:destination-21:missing-resist_conf")
    value after any fix that takes the approved path at gold >= target:
      ("2", "town:entrance-step-off:fundraising:no-safe-destination:
             depth-gate:destination-22:missing-resist_conf")
      ("2", "town:entrance-step-off:fundraising:no-safe-destination:
             depth-gate:destination-21:missing-resist_conf")

No distinction between that board (gold 15000) and this one (gold 20238)
exists other than the gold amount, so the fix cannot leave that test green
without a new threshold or a capture-keyed special case (both forbidden).
In addition, opening the set at gold >= target needs a set-end rule other
than the gold end (_end_fundraising_set_at_gold_target, policy_town.py:4790,
would close it on the next board -> reopen -> town cycle).  Choosing that end
rule (e.g. the ordinary run-count end MINING_RUNS_PER_SET, exempting this set
from the gold end the way the supply-stockout set is exempted) is a decision,
not a bug fix.
