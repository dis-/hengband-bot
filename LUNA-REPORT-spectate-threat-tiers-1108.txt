==================================================================== 1. 何を出すか

bot 側（観戦の書き出し spectate.json とコマ spectate-frames.jsonl。決定は何も読まない）:

- monsters[].threat（敵の各行）: そのモンスター1体だけを、隣にいるとして判定した結果。
    tier（"T1"/"T2"/"T3"、計算の上限を超えたら null）、instant_death と instant_death_reasons、
    skipped（"cost" なら上限超え＝不明）、irreversible（不可逆の害の種類）、worsens_with_time
    （召喚・増殖・叫び）、need_not_fight（恐怖・届かない）、selected（クエストの標的・狙う守護者・
    逃げられない・報酬）、reward（良い品・特別な品・経験値・落とし物が多い）。
  近い順に8体を超えた敵は {"omitted": "bound"}（ページは「判定省略（遠い）」）。
  ペット・友好的なモンスター、町・店・闘技場（脅威度の設計の外）は threat なし（「判定なし」）。
- threat_engagement（盤面に1つ）: 決定の記録の threat_tiers（交戦全体、今の位置での判定）から
  {"tier", "instant_death", "skipped", "hostiles"}。交戦が無ければ tier null・hostiles 0。
- monsters の並び: 即死 → T1 → T2 → T3 → 不明 → 判定省略 → 判定なし、同じ段階の中は近い順。
  threat が無い時（古い形・判定の失敗）は今までどおり近い順のまま。

1体ずつの判定に使った入口と理由:
  threat_tiers.tiered(policy, snapshot, [monster], contact=True)。
  - 「1体だけで判定」は脅威度の設計が1体の相手を判定する形で、sensed_t1_leave_key（感知範囲の
    T1 から離れる、11-08）と同じ呼び方・同じ memo の鍵。contact=True は「遠い敵がまだ来ていない
    だけで T3 に見える」のを避けるため（sensed_t1_leave_key のコメントのとおり）。隣にいる敵では
    contact=False と同じ判定になる。
  - me_powers の leave_due([monster]) は contact=False だが、これは「今その敵と戦うか」の判断なので、
    一覧の「その敵はどれくらい強いか」には contact=True の方が合う。
  - そのため交戦全体（今の位置）が T3 でも、遠くの1体が T1 と出ることがある（n1b-325 の智天使:
    交戦 T3、智天使だけなら T1）。ページの1行目に「各行は1体ずつ、隣にいるとして判定」と書いた。

費用を抑えた仕組み:
  - 1盤面1回: SpectatorWriter が盤面（snapshot オブジェクト）ごとに判定を1度だけ作る
    （threat_board）。モンスター一覧を書く時（コマを足す時か 0.25 秒ごとの書き出し）だけ呼ぶ。
    --spectate-file が無い bot では何も増えない。
  - 交戦全体は決定の記録の facts["threat_tiers"] を使い回す（_capture_decision_facts が盤面ごとに
    spectator_threat.note_engagement で覚える。盤面のオブジェクトが同じ時だけ使う）。ふつうの手番は
    記録が先なので2度目の交戦判定はしない。incident の再判断の経路だけは記録が後なので、その時は
    threat_tiers.facts を1回計算する。
  - 上限は近い順に8体（SPECTATE_THREAT_MONSTERS）。8 は自分の隣のマスの数で、殴り合いになりうる
    敵はいつも全部判定される。1体あたり 0.5〜3 ミリ秒（深い盤面の初回で最大 16 ミリ秒）。
  - 計算の上限（PROJECTION_COST_BUDGET）を超えた1体は skipped="cost" のまま「不明」と出す
    （それ以上計算しない）。
  - 決定の memo（decision_memo）そのものは使い回せない: choose_key の境目で「盤面から出した答えは
    決定の境目を越えて残さない」決まり（policy.py choose_key の冒頭）があり、protocol 3 では決定が
    見る盤面が with_known_skill_exp で作り直した別のオブジェクトで外から引けないため。代わりに
    同じ入口 tiered を使うので、同じ決定の中で呼べば memo に当たる形にしてある。
  - 判定が例外を出したら、その盤面は threat なし（「判定なし」）で書き、stderr に1時間1回まで報告。
    コマは止めない。
  - 判定は _PolicyObserverScope の中で走らせる（決定の記録の facts と同じ観察者の扱い。policy の
    状態はすべて元に戻る）。

==================================================================== 3. 色

ページの既存の色の変数だけを使った（明るい背景・暗い背景の両方で同じ変数が定義済み）:
  即死: 行の背景 --bad 30%（--panel と混ぜる）、左の帯 --bad、段階の文字は --text の太字
  T1:   行の背景 --bad 14%、左の帯 --bad、段階の文字 --bad
  T2:   行の背景 --warn 14%、左の帯 --warn、段階の文字 --warn
  T3:   背景なし、左の帯 --ok、段階の文字 --ok
  判定なし・不明・判定省略: 背景なし、帯なし、段階の文字 --muted
文字と背景のコントラスト比（WCAG の式で計算）:
  明るい: 即死の文字 10.25、T1 4.50、T2 3.57、T3 4.38、判定なし 5.30
  暗い:   即死の文字 7.98、T1 4.78、T2 5.58、T3 7.11、判定なし 5.83
  （明るい背景の T2 の --warn は太字で 3.57。既存の --warn をそのまま使ったため。名前などの本文は
  どの行も --text で 10 以上。）
color-mix() を使う（Chrome 111・Firefox 113・Safari 16.2 以降）。

==================================================================== 6. 保守性

  - 新しい処理は1つのモジュール src/hengbot/spectator_threat.py に置いた（1体ずつの判定・上限・
    並び順の表 TIER_RANK・交戦の使い回し）。観戦の書き出し（spectator.py）は並べ替えの鍵に
    tier_rank を使うだけ、cli は観察者の範囲で呼ぶ口（_spectator_threat）だけ。
  - 判定そのものは threat_tiers の既存の入口（tiered・facts・MonsterAssessment）をそのまま使い、
    新しい判定・閾値は作っていない。
  - threat_tiers.py には読み取りだけの小さな補助 outside_design(snapshot) を1つ足し、facts の
    同じ条件をそれに置き換えた（町・店・闘技場の条件を2か所に書かないため。並行の
    threat-tier-hysteresis-1108 とぶつかるとしたら facts の先頭の1行だけ）。
  - cli の protocol 3 の盤面の作り直し（with_known_skill_exp）を _decided_board に切り出し、
    facts と観戦の判定の両方で使う（同じ盤面を見る決まりを1か所に）。
  - 書き出しの1盤面1回は SpectatorWriter の threat_board だけで持つ（policy には何も書かない）。
  - ページ側は表示名・並び順・色の class を THREAT_KINDS の1つの表に、フラグの日本語を
    THREAT_NOTE_NAMES の1つの表にまとめた。並び順は bot の TIER_RANK と同じ順で、JS と Python の
    2か所にある（言語が違うため。片方を変えたら両方を変える。ページのコメントに書いた）。
  - 壁にしたテスト: なし。既存のテストの期待値は変えていない。
