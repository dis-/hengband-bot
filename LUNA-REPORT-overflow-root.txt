2. 町で所持枠を増減させる全経路の棚卸し

【新しい枠を消費し得る経路】
・Home 引き出し：通常補給、カタログ不足、識別・解呪、採掘準備、マナ食、
  戦闘武器の回収、装備トランザクション、満杯 Home の売却・廃棄用取り出し。
  開いたページと外からの atomic 引き出しの両方を store_item_key で確認する。
・店の購入：通常購入、必須補給、任意購入、Home 優先後の購入、
  in-store の連続操作、atomic/one-shot 購入、出発直前の必須購入。
  選択時 _store_purchase_fits_pack と実キー作成 store_item_key が同じ予算を使う。
・床回収：通常の拾得、固定クエスト報酬、複数品の選択、開けた箱の中身、
  マナ食装置の拾得。通常回収とマナ食は共通の床回収関数、報酬は既存の
  terminal admission、箱は回収分岐で予算を確認する。
・クエスト内の弾薬・松明・開始装備の回収、QuestFloorNavigator の拾得も列挙した。
  これらは quest floor の実行経路であり町ではない。町以外の枠条件は変更しない。
・賞金交換：C++ market/bounty.cpp は、所持している対象死体のスタック全体を
  先に除去してから景品を入れる。金銭報酬も枠を消費しないため、純増はない。
  固定クエストの床報酬は、報酬を生む操作と実際の床拾得を区別して後者を予算化。
・装備を外す／持ち替える：装備を所持品へ戻すと枠を消費する。持ち替えでは
  実際に所持している単品を先に装備する場合だけ、その枠を相殺できる。
  C++ cmd-equipment.cpp の所持品除去→旧装備 takeoff の順序も確認した。
・使用による分割：重なった杖は使用した1本の残回数が変わると分割される
  （object-use/use-execution.cpp の "You unstack your staff."）。杖の使用も予算確認。
  魔法棒の一部取得は総残回数の丸めで別スタックになり得るため保守的に1枠とする。
・銘刻：現在の銘刻操作はスタック全体に作用し、それ自体は分割しない。
  ただし銘の違いで取得品が合流しなくなるため、取得見積もりで銘も比較する。
  識別・充填・強化も、表示や合流条件の変化と、実際の分割操作を区別した。
・自動拾得：町で床品へ歩くと、賞金首死体等は C++ autopick.cpp から自動取得される。
  隣接候補と歩行の実行点も同じ予算を使う。native travel は次の観測までに
  複数の床品を横切れるため、表示された床品の総数を収容できなければ歩行へ戻す。

【空きを作る経路】
・Home 預け入れ（ページ／atomic／バッチ、装備整理）：スタック全体を出せば1枠。
  予約の残る一部預け入れは枠の解放として数えない。
・合法な売却（通常候補、組織化候補、銘刻確認後の sale executor）：全量売却で1枠。
・有用な使用（能力回復・能力上昇・経験回復、飲食、巻物、補充、装備への移動等）：
  最後の個数を使い切った観測で初めて枠が空く。装置の残回数消費だけでは空かない。
  取り込んだ main の Magic-Eater の道具吸収も、道具が実際に消えた観測で空きを数える。
・合法な破壊：既存 junk 判定・破壊検証器で全量を破壊した場合のみ。
・同種スタックの合流：最大99個、銘・既知状態・修正値・残回数等の違いを考慮。
  合流を証明できない取得は1枠と見積もる。
・投棄・投擲で枠は空くが、町の回収ループを作るため overflow 救済には追加しない。
  クエスト中の既存投擲・箱の投棄、賞金対象の提出は既存の目的に限る。

3. 根本修正と既存の判断の維持

town_pack_budget.permits が最低4枠の判断を一元所有する。
新しい枠を消費するなら、操作後も4枠以上を残す。既に不足している盤面でも、
枠を増やさない操作・回復操作は許可する。将来の売却予定は空きとして先取りしない。
実際の次の所持品観測か、同一の装備コマンド内で先に確定する単品除去だけを信用する。

通常の預け入れ・売却候補の順序は保ち、その後に未予約の既知の消耗品・道具を
Home へ保存する候補を足した。Home が満杯／預け入れ不可なら、同じ品を
既存 organization-sale の計画と実際の店内売却器まで接続する。
最終停止の直前にある既存の town-plan の overflow 所有者から救済を実行する。
破壊だけを指定する低水準 API の既存動作は保ち、公開選択経路では必ず
try_relief=True を指定する。全ソースの呼出しを検査する構造ピンで迂回を防ぐ。
Home の情報が不明なら既存の観測所有者へ依頼し、Home 預け入れ→売却→
有用な使用を試し、その後に従来の破壊・停止処理へ進む。
明確な junk は従来の junk 所有者へ渡し、保管用の新候補には混ぜない。

retention_reservations、識別・装備トランザクションによる所有、拒否済み品、
店ごとの拒否、訪問回数制限を維持した。目的購入品は使用前に売却しない。
10/20 の junk 範囲、10/21 の重量に合わせる購入数量（弾薬だけ）、#96 の方針を
変更していない。一般品の比較に重量制限を追加していない。
既存テストの期待値は書き換えていない。

6. 保守性と作業範囲

取得の合流見積もりと枠予算を小さな専用モジュールにまとめ、店の選択と
実キー作成で再利用した。救済は既存の Home・売却・使用・経路の所有者へ
委譲し、別の生キー生成器や別の予約台帳を作っていない。
新しいアダプターとデータ関数を work manifest のレビュー表に明示し、
claims / ladder / terminal の構造検査にも接続した。
上限対象ファイルは取り込んだ main の行数を増やさず、変更領域の説明を短くした。
実ゲームの稼働プロセス、他の作業者の作業ツリー、公開中の PR、配備先には変更していない。
fast_tier 用に同一 HEAD の一時チェックアウトを作成し、mutation のソース巻き戻しから
隔離した。検証本体の実行状況は5節に記載した。
一時チェックアウトは除去済み。実行・待機したプロセスは終了を確認し、未完了のものを残していない。
