Loop
----
choose_key -> _decide -> _home_full_relief_key -> _home_deposit_batch.
The recently purchased *Remove Curse* scroll in slot h is explicitly selected
for Home's reserve. Ordinary _retention_surplus is zero because visit-purchase
retention protects it. The old batch consequently appended nothing, never
marked the slot selected, and left simulated inventory unchanged. Its next
_find_home_deposit selected the same slot. The selected-count limit could never
advance, so the loop was infinite rather than a slow quest-offer scan.

Other candidates' retention evaluations repeatedly call
_carry_procurement_strategy(cache_fixed_quest_head=False), which calls
_uncached_fixed_quest_head and _fixed_quest_is_offered. The ten-second sample
counted 5,973 offer calls, all from _uncached_fixed_quest_head, and 1,991 quest
order calls. This explains watchdog samples in quest/supply functions while
the actual non-progress loop is in Home batching.

Fix
---
Share the explicit reserve-transfer predicate and quantity across selection,
batch simulation, actual deposit command and retries. A pending reserve moves
one scroll into Home even when ordinary pack retention protects that purchase;
pending withdrawal/inflight ownership still disables the exception. Ordinary
items retain their usual retention rules. Compute batch quantities using the
same simulated inventory used by selection.

A zero-quantity stale candidate now stops visibly with
shop_selector.home_deposit_batch_refusal = {slot, reason: no-simulated-surplus}.
The final diagnostics pass preserves that marker only for its decision, and
the existing JSONL writer logs shop_selector. This is an additional diagnostic
stop; the real fix supplies the missing reserve-transfer quantity. No time
guard, resistance/depth-rule change, or extra game knowledge was introduced.
