## Measured diagnosis

`LUNA-DIAG-chest-await.txt` records the replay details. In `captures-chest/state.jsonl`, row 209 / turn 77068 is quest 34 at `(8, 17)` with five processable chests in slots `i-m`. The captured decision row 197 posts `di` with `chest:drop-unreachable-reserved`. Row 210 / turn 77073 has four processable chests in slots `i-l`, remains at `(8, 17)`, and reports that chest `(i)` was dropped and that the player no longer carries a chest. Captured decision row 198 instead posts `5` with `chest:await-drop`; later records repeat this wait.

Replaying both state rows through `parse_snapshot` and the real `_chest_processing_key` on base `4e68bc66`, with the origin outside the reserved quest positions, returned `5` / `chest:await-drop` for both. The old branch waited because it checked whether *any* processable chest remained (4 on the post-drop board), rather than whether the posted chest remained carried. The underfoot fallback was below that check. The captured board also encoded the origin chest in the grid map, but that cell was outside the allowed reserved positions for this quest replay.

## Change and pins

The policy now stores the processable-chest count when it posts either reserved-route or ordinary `chest:drop`. A pending drop keeps waiting while the observed count is unchanged; a count decrease settles the posted operation and lets the existing origin fallback continue. The existing displaced chest search still runs first. Route selection, chest opening, trap handling, and quest sweep behavior were not changed.

`tests/fixtures/chest-await-q34-20261015.jsonl.gz` contains only the two captured state rows, raw UTF-8 JSONL inside a small gzip fixture (3,268 bytes). `tests/test_chest_await_drop_recorded.py` replays them through the actual policy. On the pre-fix base, the post-drop board repeatedly returned `5` / `chest:await-drop`; the baseline run of the new module passed with that behavior pinned before the source fix. After the fix, the same repeated turn-77073 board returns key `7` / `chest:step-off`.

Controls in the new module:

- Unchanged carried count continues to return `5` / `chest:await-drop`.
- A pending drop with no count baseline remains conservative while a chest is carried.
- A normal single chest drop returns `di` / `chest:drop`, waits while it remains carried, then proceeds with key `7` / `chest:step-off` after it is dropped.
- A normal multi-chest drop settles when the carried count falls even though another chest remains.
- A displaced chest within three squares is adopted and returns `s` / `chest:search`.

Existing assertions were left unchanged. The existing `tests.test_policy_identification` module passed (48 tests); `tests.test_policy_quest` passed (334 tests, 7 skipped).
