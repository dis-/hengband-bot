1. 診断（保存資料の実測）
結論: 戦士 Lv7 と魔道具術師 Lv1 の owner-retired-burst は同じ原因。
4件とも、未投稿の光源装備取引が店舗移動を拒否する一方、町の優先 owner は
脱装備済みの復旧債務がある場合にしか取引を実行しなかった。まだ何も脱いでいない
最初の equip が取り残され、route-refused → shop:approach の 5 → breakout を反復した。
退役したのは equipment-txn 自身ではなく detectors（breakout）。直前 owner は store-router。
再帰 recurrence_count=2 / limit=2 に達し、1回の失敗でも退役している（単純な予算枯渇ではない）。
3回の無進展退役を CLI が burst として停止した。停止監視や退役予算は緩めていない。

no-key-exhausted 4件は同じ停止表示への別経路。life-400 は Q1 準備済みでも隣接猫への
戦闘を引き継がず quest-entry-unavailable。life-226 の3件は売却対象の松明の @v0=g を
売却 owner が上書きせず拒否するが、同じ棚の購入 owner に渡さず退店。General の
入口 (31,119) と隣接セル (32,118) を往復し no-progress:fundraising-digger で空キーになった。
この3件は再起動による反復で、4種類の別キャラクターではない。

2. 修正
町の装備 owner を、復旧債務だけでなく未完了取引の最初の操作から実行する。
見失った equip 対象は理由を equipment-transaction:equip-item-missing と明示し、既存の放棄・再計画へ渡す。
Q1 開幕 owner は、買物以外の段階でも隣接脅威を解決する。遠方を追う従来の優先順位は維持する。
売却の銘を安全に付けられない場合は既存の購入選択・Home確認・予約・投稿判定を通じて同じ棚の購入へ渡す。
銘の上書き、必要抵抗・光源/燃料条件、ジャンク範囲、荷物余裕、開幕順序、購入予算は変更しない。
保守性: 購入選択から実行までを小さな shop_purchase_dispatch.py に集約し、コピーされた処理を削減した。
policy.py / policy_shop.py は減行。上限ファイルへ新規ロジックを積み増していない。既存テストの期待値は変更しない。

3. 検証範囲・限界
8 incident の盤面、判断、診断状態、知識応答、品物原本、出典 SHA256 を fixture に固定。
public choose_key と production follow executor を使用。ゲーム側の操作結果は明記した構成応答であり、実機の新規人生完走ではない。
装備 session オブジェクトは診断 JSON に入らないため、transaction_next と同じ出典の元の品物から再構成する。
life-226 の Black 棚は64品中の末尾12品しか保存されず、開幕ページ census も診断に未保存。再開時に棚を再観測する。
テストではその12品だけになった再入荷を明示的な構成応答とし、General を改めて観測して採掘道具購入まで通す。
欠けた52品や当時の全棚を再現できたとは主張しない。停止監視を弱める方法で pin を通していない。
